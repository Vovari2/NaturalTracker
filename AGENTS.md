# Работа с NaturalTracker

## Начало каждой сессии

1. Полностью прочитать актуальный `README.md` в корне проекта до начала работы. Использовать его как основной обзор назначения, возможностей, ограничений и публичного API проекта; учитывать прочитанное при выполнении задачи.
2. Прочитать `CLAUDE.md`: проект ранее сопровождал Claude, и пользователь просит сохранять его подход, стиль кода и принятые соглашения. Эти инструкции применять вместе с настоящим файлом.
3. Прочитать `agent-work/notes/project.md` для восстановления контекста предыдущей работы. Заметки сверять с текущими исходниками: они не заменяют код и README.
4. Проверить `git status --short` и относящиеся к задаче изменения. Сохранять незавершённую работу пользователя.
5. Перед изменениями прочитать затрагиваемые исходники, ресурсы и Gradle-конфигурацию. После перерыва или восстановления контекста перечитать файлы, содержание которых могло измениться.

## README — часть каждой задачи

- При каждом изменении проверять, соответствует ли `README.md` фактическому состоянию проекта.
- Если меняются возможности, поведение, требования, установка, сборка, команды, права, настройки, API, события, плейсхолдеры или ограничения, в той же задаче вносить необходимые точные изменения в README.
- Описывать реализованное поведение. Не выдавать планы и неподтверждённые предположения за существующие возможности или результаты проверки.
- Сохранять русский язык, понятный стиль и полезные примеры существующего README. Не переписывать его целиком без необходимости.
- Исходная версия README сохранена побайтно в `.codex/backups/README.2026-11-23.original.md`. Не менять и не перезаписывать эту копию; актуальную документацию вести в корневом `README.md`.

## Подход и соглашения

- Работать в существующей архитектуре и стиле, описанных в `CLAUDE.md`, с минимальными изменениями по задаче.
- Текущий код изменять только по необходимости и по минимуму; не добавлять попутный рефакторинг.
- Общение с пользователем, сообщения плагина, логи и новые комментарии — на русском языке.
- Java 17, Gradle Wrapper, модули `core` и `api`. Версия проекта задаётся в корневом `build.gradle`.
- Кэш чанков и Bukkit API использовать из главного потока; операции чтения и записи чанков в БД выполняются через `SerialWorker` со снимками данных.
- Публичные `NaturalTrackerAPI` и классы событий продублированы в `core` и `api`. При изменении сохранять согласованность обеих копий.
- Настройки согласовывать между `Settings`, `settings/Loader`, `core/src/main/resources/settings.yml` и README. Тексты сообщений добавлять через `Messages`, выводить через существующие MiniMessage-обёртки.
- Не менять версии, зависимости, формат БД, структуру модулей и настройки IDE без необходимости для задачи.

## Рабочие папки

- По просьбе пользователя содержание сессий, рабочие заметки, планы и логи сохранять вне `.codex`, в обычной папке проекта `agent-work/`. Не выбирать для них служебные `.codex` или `.agents`. Сохранять необходимые заметки в рамках текущей задачи без отдельного вопроса о сохранении сессии, соблюдая действующие разрешения среды.
- `agent-work/notes/` — устойчивые сведения о проекте, решения, итоги сессий и результаты проверок. Обновлять при существенном изменении контекста.
- `agent-work/plans/` — планы сложных задач, когда они нужны; простые задачи не требуют отдельного плана.
- `agent-work/tmp/` — временные файлы и логи, исключённые из Git.
- `.codex/backups/` — явно сохранённые исходные версии документов. Не использовать вместо истории Git для каждой правки.
- Старые `.codex/notes/` и `.codex/plans/` оставлены как архив начального знакомства; актуальные записи находятся в `agent-work/`, старые не обновлять.
- Сгенерированные `build/`, `core/build/`, `api/build/`, `.gradle/` не являются исходниками; не читать их без необходимости проверки конкретного артефакта.

## Проверка результата

- Подбирать проверки по изменениям. Для правок только документации достаточно проверки содержимого, ссылок и `git diff --check`.
- Никогда не запускать компиляцию или сборку без отдельной явной просьбы пользователя в текущей задаче. Это относится и к `shadowJar`, `build`, `runServer` и другим задачам, которые запускают компиляцию как зависимость. Прежнее общее разрешение на `shadowJar` отменено; просьба изменить код сама по себе не разрешает компиляцию.
- Когда компиляция прямо запрошена, для изменений Java начинать с `./gradlew.bat :core:compileJava :api:compileJava` в PowerShell; в POSIX использовать `./gradlew`. Файлы тестов не создавать.
- По явной просьбе запустить сервер использовать `./gradlew.bat :core:runServer` (в POSIX — `./gradlew :core:runServer`), а не прямой запуск через `java -jar`. Эта задача также выполняет сборку.
- Автоматических тестов сейчас нет. Изменения поведения проверять на Paper и явно сообщать, если серверная проверка не выполнена.
- `:core:shadowJar` пишет JAR прямо в `D:\Minecraft\Servers\Paper 1.20.1\plugins\`, а `:core:runServer` собирает его и запускает сервер. Учитывать эти побочные действия и действующие разрешения среды; для обычной проверки документации они не нужны.
- В конце кратко сообщать, что изменено, что проверено и какие проверки остались невыполненными.
